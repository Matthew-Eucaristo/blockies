Blockies explorations

Eight versions of the core idea, each built, played with and written up, to help Matthew and Edward decide. They all share one substrate: a lattice that never knows its own dimension, with renderers that decide whether it is a flat board, voxels, or a space-time sculpture. These are sketches in JavaScript, not the core: whatever is chosen gets built properly in the Rust crates.

Each page has Idea, editable Spec (exactly what an agent would write, with its size) and Notes (what happened when I tried it). Keys: 1 flat, 2 voxel, 3 space-time, space pause, . step.

The eight versions

Organism 1

Every computer is a pure function with a body. Props flow down and outputs flow up the tree. The shape is the state.

Found: a queue as a growing tail reads instantly, but bodies collide.

~1.8k charstree sharing

Messages 2

Computers are actors. Messages are tokens that walk the lattice, so distance is latency, and overload emerges as visible mailboxes.

Found: in a 1D world, Space-time is a sequence diagram nobody drew.

~2.0k charsmessage sharing

Signals 3

Blocks only sense what they touch. Wires carry a fading level. The ASCII picture is the program, in 2D or 3D.

Found: a timing diagram for free, and that I (an LLM) wire things wrong.

~1.3k charsadjacency sharing

Rules 4

A computer is a list of rewrite rules (data, not code). One rule grows a maze in 2D and a labyrinth in 3D.

Found: the tiniest programs, and a natural answer to who owns a cell.

~0.3k charsshared space

Mind 5

An agent's work as a living process tree: one block per process; waiting is hatched; children grow around parents.

Found: the same run as a 1D world is a Gantt chart with the critical path.

~1.9k charsspawn and results

Sheet 6

A spreadsheet in space: formulas, declared finite states, and changes that travel as pulses you can follow.

Found: cause and effect are visible, but nothing is really a process.

~1.1k charsformula reads

Kernel 7

The synthesis: processes with bodies, talking only by messages. Agents say what; the lattice decides where.

Found: autoscaling becomes a shape, and the moat rule.

~2.9k charsmessages + bodies

Nest 8

A computer can contain a world. Complexity comes from depth, and every level stays small, with live miniatures.

Found: 25 computers, four levels, never more than six on screen.

~2.0k charscontainment

Three discoveries (things I only found by trying)

1. Diagrams are views of running worlds

Because the lattice does not know its dimension, time can be one more axis. When I put actors on a 1D world and stacked ticks, a sequence diagram appeared without anyone drawing it. The binary counter gave a timing diagram. The agent's process tree gave a Gantt chart with the critical path. In 2D, history became a sculpture you can look at.

So "the renderer decides" is bigger than 2D vs voxel. The classic diagrams developers draw by hand (sequence, Gantt, timing, flame graph) are projections of world × time. With Blockies you never draw them: you run the system and look at it from another angle, so the diagram cannot drift from reality.

2. Agents should say what, never where

In Signals I wired a lever backwards and left a diagonal gap. Both were coordinate mistakes, and agents will make them too. In Kernel the agent only says how much body a process has and which children it spawns. The lattice places everything, so that whole class of errors disappears. For an agent-driven product this matters more than any visual choice.

3. Space must be owned, and cores need a moat

Bodies collided in Organism and Messages. Rules answered it simply: first come, first served. Kernel then hit a subtler bug: a growing queue buried its own workers. The fix is a rule, a body may never touch another computer's core. It is a candidate answer to Edward's question "how do blockies interact visually": they push, flow around, and keep each other visible.

A candidate core (for discussion, not decided)

If I had to propose one direction, it would be Kernel + Nest + views, with Rules as the engine for [d] materials:

  1. Lattice of any rank; renderers decide (board, voxel, terminal, space-time diagrams, and even voice).
  2. Computer [c] = one process = one block: a pure step(state, io) that may send, spawn, wait, finish or fail. A kind is a type of blockie.
  3. Sharing only by messages, including from people (a click or a voice command is a message). There are three state models: a computer's own state, messages, and the containing world.
  4. Drawing [d]: a computer declares how much body it has; the lattice grows it through free space, with first come, first served and the moat rule. Rewrite rules can drive materials (sand, water, growth).
  5. Nesting: a computer may contain a world; messages cross levels only through the container.
  6. Determinism everywhere: same spec plus same inputs gives the same world. That gives replay, sharing a world as a link, and time travel, and it is what the Rust lockstep engine already does.

Questions for Edward

  1. In the sketch, block 1 is blue and 2 and 3 are red. Is 1 a parent, a different kind, or selected?
  2. Block 4 is hatched. Waiting, sleeping, crashed, or not yet placed? (Mind and Kernel use hatched for waiting.)
  3. What is the blue vertical line that runs past the frame? A timeline or playhead (Space-time would fit), a viewport edge, or a boundary between worlds?
  4. Is orange the kind ([d]) or the owner? Owner tint made bodies much easier to tell apart.
  5. Do [d] blocks belong to exactly one [c]? Can a [d] exist on its own (terrain, sand)?
  6. Pure functions: is a computer's state inside it (actor style) or passed in and returned (Elm style)? Kernel does the second.
  7. Is the green process bar part of the product, or only a diagram aid?
  8. Which of the three discoveries fits the vision, and which does not?

Ideas not built yet

  • Agent adapter: Claude Code hooks (tool calls, subagents) → Mind processes. A live view of a real agent.
  • Telemetry adapter: OpenTelemetry spans → processes. Production as a living world.
  • Narrator renderer: speaks the world ("the API queue is growing") for voice-first use.
  • Sound renderer: each process a voice; load as pitch.
  • Fork and diff: branch a world at tick t, run "what if", and colour the cells that differ.
  • Watchers: invariants as computers that turn red (property tests you can see).
  • Capabilities: a computer can only message what it holds a handle to (safety for agents).
  • Turtles: computers that move and leave [d] trails; drawing as the path of a process.
  • Soft bodies: [d] blocks on springs that wobble under load.
  • Algorithms in 1D: sorting as a line, where Space-time shows each algorithm's signature.
  • Budgets: compute or energy per computer, visible as body mass.
  • Orbit voxel renderer (WebGPU) for real 3D, plus cutaways.

Where this could go

The novel part is not the whiteboard. It is computation with a body: every process is visible, its shape is its state, it is deterministic and replayable, and diagrams are views of it. Today code is invisible, observability is dashboards and logs, and diagrams are drawings that drift from the truth.

Why it is not AI slop: slop is output that looks plausible and has no ground truth. A Blockies world runs, so it is either right or visibly wrong, and anyone can replay it and get the same hash. An agent that explains something by building a world is accountable in a way a generated picture is not.

Wedges that could make waves (each one demo-able in a short video):

  1. Watch your agent think: a live world of Claude Code's tool calls and subagents, with pause by click or voice.
  2. Explorable explanations on demand: "explain Raft" builds a world of nodes and messages, and the sequence diagram appears by itself.
  3. Never draw a diagram again: describe the system, run it, and switch views (board, sculpture, sequence, Gantt).

As an OSS foundation: a small deterministic kernel (Rust, WASM), an open world format and protocol, and pluggable renderers and kinds that others write (terminal, web, voxel, VR, sound). Each discovery above is also a technical blog post, which fits Edward's plan of building a name through writing and open source.

The risk: "a world engine" is hard to explain. It needs one sharp first use case, and I would pick wedge 1 or 2.
